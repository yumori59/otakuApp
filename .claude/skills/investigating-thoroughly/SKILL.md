# 徹底調査 (結論の前に全経路と反証)

## Overview

調査の失敗は **見つけ損ない** と **誤認** の 2 種。網羅は複数軸、正確さは主張単位の裏取り。
「詳細な報告」≠「正確な報告」。読者は検証せず転記する。

## ステップ

### ① 問いの確定

何を判断するための調査か (答えの使われ方) を 1 文にしてから探す。
曖昧なら解釈を列挙し最有力を選び、報告に明記する。

### ② 多軸探索 — 1 軸で打ち切らない

- 軸: 名前 / 内容 / 利用側 / テスト / 履歴 (`git log -S`)
- 知識は **apps/api (dto/service)・meigicho (Domain/Network/Features)・Prisma・docs/** に散在する
- 「見つからない」は別軸で 2 回探してから

### ③ 経路の完全列挙

同じ機能に複数経路がないか確認する（ローカル SwiftData / Sync / 実 API、共有 Web、モック）。
未使用に見える View・API は遷移元・呼び出し元を grep してから未使用と書く (IOS-1)。

### ④ 比較主張の裏取り

「同等」「対応済み」の前に、比較次元ごとに**両方のコードを読んで**差分確認する。

### ⑤ 反証探索

結論に反する証拠を 1 回探す（else、フォールバック、環境フラグ、既存テスト期待値）。

### ⑥ 報告

- 事実は file:line。推測は明記
- 未調査範囲を書く。「見つからなかった」≠「存在しない」
- 転記値は一次ソースへ再照合

## よくある間違い

| 間違い | 現実 |
|---|---|
| 片方だけ精読して「同等」 | 両方読む |
| 最初のヒットで結論 | 多層・多軸で 2 周 |
| 「見つからない」=「無い」 | 軸を変えて再探索 |
| 推測を事実の顔で書く | 誤認は成果物まで到達する |
| 未接続コードを省略 | 食い違いはリスク。存在は報告 |

## 実例メモ

このリポジトリでの調査失敗パターンが溜まったら、本節を実例で更新する。
移植元では「ユーティリティは対応済みだが経路途中の service が黙殺フォールバック」型の見落としが典型だった (BE-2)。
