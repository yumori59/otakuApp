## Q1. 共有時のマスキングは維持するか、これも撤回するか

**この計画で最も重要な未確定点。** ユーザーの回答（「全桁を平文で保存・常時表示」）が
「オーナー本人の画面」だけを指すのか、「共有先の画面」まで含むのかは確定していない。

| 選択肢 | 内容 | 影響 |
|---|---|---|
| A | **維持**。共有ボードには会員番号を一切含めない（現状の構造的保証をそのまま） | 実装変更ゼロ（F5 の禁止キー検査もそのまま通る）。`docs/08` §4.2 の対策 5 が生き残るので、法務説明が成立する |
| B | 撤回。共有先にも全桁を見せる | `shares/board/` のペイロード組み立て・DTO・spec・`docs/04` §3.7.6 の契約変更。**他人の個人情報を第三者に開示する経路**を新設することになり、`docs/08` §5.1.2（第三者提供）に直接抵触する |

- **デフォルト仮定: A（維持）**
- 理由: ユーザーが選んだのは「保存・表示」の方式であって、「第三者への開示」ではない。
  B はアプリ内の表示変更ではなく**第三者提供の新設**であり、個人情報保護法上の論点が別に立つ。
  A なら実装差分ゼロで、撤回範囲を「オーナー本人の閲覧」に限定できる。
- **実装前に人間の確認を要する。** A のまま進めるが、B だった場合は本計画を作り直す。

`[Answer]:` **A（維持）**。共有先には会員番号を出さない（2026-08-20 ユーザー確認）。

## Q2. `mask_member_no` フラグをどうするか

F6 のとおり、この API フィールド・DB 列は現状**何も制御していない**（board ペイロードに会員番号が無いため）。

| 選択肢 | 内容 |
|---|---|

  「現状このフラグは board ペイロードに影響しない」旨のコメントを 1 行足して、実態と契約の乖離を明示する。

## Q3. 列名をどうするか

| 選択肢 | 内容 |
|---|---|
| A | **`member_no_last4` → `member_no` にリネーム**（1 列のまま意味と名前を揃える） |
| B | `member_no` を新設し `member_no_last4` を残す（併存） |
| C | 列名は据え置きで、中身だけ全桁にする |

- **デフォルト仮定: A**

- 却下の代償: リネームは既存行の値の扱いを決める必要がある（Q4）。

## Q4. 既存データの移行方針

下4桁しか保存されていないため、**全桁は復元不可能**。

| 選択肢 | 内容 |
|---|---|
| A | 既存行の値をそのまま `member_no` へ移す（下4桁のまま残り、次に編集したときに全桁になる） |
| B | 既存行の値を NULL にする（「不完全な値」を残さない） |
| C | 未出荷なので開発 DB を作り直す（データを気にしない） |

- **デフォルト仮定: A**
- 理由: B はユーザーが自分で入れた情報を運営都合で消すことになる。A なら「4821」が残り、
  ユーザーが必要なら上書きできる。
- **前提の確認が要る**: 本番 DB / TestFlight 配布済み端末に守るべきデータが存在するか。
  F7（SwiftData は「出荷前」前提）と `CLAUDE.md`（本番運用前に必須の項目が残っている）から
  **未出荷と推定**しているが、推定のまま破壊的変更はしない。
  未出荷なら C で足り、Q5・Q6 の互換対応もすべて不要になる。

`[Answer]:` **未配布（開発中のみ）**。本番 DB・TestFlight 配布いずれも無し（2026-08-20 ユーザー確認）。
選択肢 **C**（未出荷なので開発 DB を作り直す）を採用する。

## Q5. 旧クライアントとの同期互換（Q4 で「配布済み」の場合のみ）

F8 / F9 のとおり、iOS の書き込みは `POST /v1/sync/push` を通り、**未知キーは黙って捨てられる**。
列名を変えると、更新していない端末が送る `member_no_last4` が無視され、**会員番号が黙って消える**。

| 選択肢 | 内容 |
|---|---|
| A | 互換不要（未出荷。Q4=C の場合） |
| B | `sync-payload.mapper.ts` で移行期間だけ `payload.member_no ?? payload.member_no_last4` を受ける |

- **デフォルト仮定: A**（Q4 の回答が「未出荷」である前提）
- Q4 で配布済みと分かった場合は **B が必須**。かつ「未知キーを黙って無視する」現状の挙動自体が
  BE-2 の観点で危ういので、そのときは移行期限も併せて決める。

`[Answer]:` **A**（未配布のため互換対応は不要。Q4 確定に伴う）

## Q7. 入力バリデーション（全桁を受けるときの許容文字と長さ）

現状は `/^[0-9A-Za-z]{1,4}$/`（F4）。F12 のとおり実際の会員番号はハイフンを含む形式がありうる。

| 選択肢 | 内容 |
|---|---|
| A | `@IsString() @MinLength(1) @MaxLength(64)` + 制御文字禁止のみ（文字種は絞らない） |
| B | `/^[0-9A-Za-z\-_/. ]{1,64}$/`（英数 + 一部記号のみ） |

- **デフォルト仮定: A**
- 理由: B は全角文字や FC 独自の記号を含む会員番号を 400 で弾く。会員番号は
  **検索も集計もしない、保存して見せるだけの項目**（`docs/08-compliance-risk.md:356` の分析がそのまま使える）なので、
  文字種を絞る実利が無い。長さと制御文字だけ制限する。
- iOS 側は **`prefix(4)` の黙った切り捨てを撤去**する（F3 は BE-2 の「黙殺フォールバック」の iOS 版）。
  64 文字を超える入力は入力段階で打ち止め（切り捨てではなく入力不可）にする。
