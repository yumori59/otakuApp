# application-edit — 確定が必要な論点

ユーザー原文: 「作成したツアーの内容（同行者など）を編集できるようにして欲しいです」

**用語のズレ（先に確定済みの事実）**: 同行者は Tour ではなく **Application（申込）に紐づく**
（`apps/api/prisma/schema.prisma:214` `ApplicationCompanion.applicationId` / `docs/01-product-overview.md:266-270` 用語集）。
Tour は `id/ownerId/artistNameRaw/name/events` のみで companions を持たない（`schema.prisma:149-163`）。
したがって要望の実体は **「申込の編集」** と解釈する。

各 Q は「未回答でも計画を止めない」ためのデフォルト仮定を置いてある。
**回答が来たら `[Answer]:` 行に書き戻し、differ があれば `requirements.md` / `plan.md` を更新する。**

---

## Q1. 編集できる範囲

| 選択肢 | 内容 | 影響 |
|---|---|---|
| A | 同行者だけ | 実装最小。ただし「公演名を打ち間違えた」は直せないまま残る |
| B | 申込側だけ（代表者・同行者・申込日・当落発表日・ステータス・座席・メモ）。公演情報は読み取り専用 | 他申込への波及ゼロ。ツアー名/公演名の訂正はできない |
| C | 追加フォーム（`AddApplicationView`）と同じ 12 項目すべて | 訂正手段として完結。公演情報の変更は同じ公演を参照する他申込に波及する（Q3） |

- **デフォルト仮定: C**
- 理由: 原文の「同行者**など**」は範囲を限定していない。かつ現状 `AddApplicationView` で入れた公演名・会場・公演日を後から直す手段が**アプリ内に一切ない**（`ApplicationDetailView` の書き込みは status と seat のみ = `ApplicationDetailView.swift:99,153`）。訂正不能なフィールドを残すと「作り直して古い方を消す」しかなく、削除 UI も無いため詰む。

`[Answer]:` C（ユーザー確定・2026-08-12）

## Q2. 「ツアー名」を変更したときの意味

Tour は複数の申込から共有される（`(owner, name)` で一意 = `schema.prisma:161`）。

| 選択肢 | 内容 | 影響 |
|---|---|---|
| A | ツアー名は編集不可（表示のみ） | 安全だが訂正できない |
| B | **付け替え**: 入力名で find-or-create し、この公演(event)を別ツアーへ移す | 他申込に波及しない。元ツアーが空になることはあり得る（`tours.remove` は連鎖しない仕様なので放置される） |
| C | **リネーム**: 当該 Tour の name を書き換える | 同ツアーの全申込の見出しが変わる。既存名と衝突すると BE で `CONFLICT`（`tours.service.ts:56-63`）。同期 push 経路では Prisma の unique 違反になる（後述リスク） |

- **デフォルト仮定: B（付け替え）**
- 理由: 追加フォームのツアー名欄はすでに find-or-create の入力（`AddApplicationView.swift:40-55` のサジェスト）であり、編集でも同じ意味にするのが平仄。C はユーザーの意図（「この申込のツアー表記を直したい」）を超えて他申込を巻き込む。

`[Answer]:` B（ユーザー確定・2026-08-12）

## Q3. 公演情報（公演名・会場・公演日）を他の申込と共有しているとき

同一 `event_id` に代表者違いの複数申込を持つのは**仕様**（R2-3 / `docs/01-product-overview.md:70`）。

| 選択肢 | 内容 |
|---|---|
| A | 更新する。ただし他申込があるときは保存前に「この公演を参照する他 N 件にも反映されます」と明示 |
| B | 他申込があるときは公演情報を編集不可にする |
| C | 編集時に event を複製して自分の申込だけ差し替える |

- **デフォルト仮定: A**
- 理由: 会場名・日付の訂正は本来「公演そのものの訂正」であり、全員に反映されるのが正しい。C は同一公演の event 行が増え、重複申込検知（R2-8 / `DuplicateApplicationDetection`）とツアー表のグルーピングが壊れる。

`[Answer]:` A（デフォルト仮定を採用・2026-08-12）

## Q4. アーティスト名の変更

アーティスト名は Tour の属性（`Tour.artistNameRaw`）。付け替え（Q2-B）をしない限り同ツアーの全申込に反映される。

- **デフォルト仮定: 当該 Tour を更新する。UI に「同じツアーの申込すべてに反映されます」の注記を出す**
- name と違い unique 制約が無いので衝突しない。

`[Answer]:` 上記（デフォルト仮定を採用・2026-08-12）

## Q5. 申込の削除 UI を同時に入れるか

`ApplicationRepository.delete` / BE `DELETE /v1/applications/:id` は実装済みだが、**呼び出す UI が無い**。

- **デフォルト仮定: 入れない（本計画のスコープ外）**
- 理由: 要望は編集。削除は取り消し不能操作で確認 UI・誤操作対策の設計が別途要る。必要なら別計画 `docs/plans/application-delete/` を立てる。

`[Answer]:` スコープ外（デフォルト仮定を採用・2026-08-12）

## Q6. 追加フォームに無いフィールド（`round_name` / `ticket_count` / `price_yen`）を編集画面に出すか

DB と API には存在するが（`schema.prisma:190-196` / `update-application.dto.ts:42-79`）、`AddApplicationView` は送っていない。

- **デフォルト仮定: 出さない**
- 理由: 追加フォームと非対称になり、「編集でしか入れられない項目」が生まれる。出すなら追加フォーム側も同時に変える（別スコープ）。

`[Answer]:` 出さない（デフォルト仮定を採用・2026-08-12）

## Q7. ステータス・座席を編集画面にも置くか（詳細画面と二重になる）

- **デフォルト仮定: 置く**
- 理由: 追加フォームに両方あるため（`AddApplicationView.swift:102-111`）、編集で消えていると「減った」と受け取られる。詳細画面のワンタップ切替（R3-1）と座席インライン編集（R3-2）は仕様なので**そのまま残す**。値の源は常にレコード 1 つなので二重更新にはならない。

`[Answer]:` 置く（デフォルト仮定を採用・2026-08-12）

## Q8. `AddApplicationView` の扱い

| 選択肢 | 内容 |
|---|---|
| A | 共通の `ApplicationFormView(mode: .create/.edit)` に統合 |
| B | `EditApplicationView` を別実装 |

- **デフォルト仮定: A（統合）。ただし「振る舞い不変の抽出リファクタ」と「edit モード追加」を別タスクに割る**
- 理由: 12 フィールド・同行者 3 系統の UI を二重管理すると必ずドリフトする。一方で既存の追加フローの回帰は避けたいので、リファクタ単体でレビューできるように分ける。

`[Answer]:` A（デフォルト仮定を採用・2026-08-12）
