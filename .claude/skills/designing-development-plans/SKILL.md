# 開発計画の設計 (現状把握 → 設計判断 → 検証可能な分解)

## Overview

計画の品質は **現状把握の深さ** で決まる。把握を飛ばすと計画全体が無効になる種類の事実がある
（実装済み未配線、キー設計の移行途中、要件語の実体ズレ）。

AIDLC ライト (`01-aidlc.md`・aidlc-planner) はフェーズと成果物を定める。
本 skill は各フェーズで何を考えるかを定める。

## ステップ

### ① 現状把握が先

- 近縁機能が BE / iOS / DB の 3 面に既に無いか grep。部分存在なら「ギャップ分析」
- 要件キーワードの実体をコードと `docs/` で特定。**仕様の正は `docs/`**
- データの同一性とライフサイクル（ID は UUID v7 クライアント発行）
- **死んでいるコードを手本にしない**（呼び出し元の存在を先に確認）

### ② 設計判断には理由と却下案

採用案 + 却下した代替と理由。根拠は既存コード一貫性 (file:line)。
迷ったら振る舞いロジックは BE（jest）に置く。

### ③ 影響範囲の層チェックリスト

- DB: `apps/api/prisma/schema.prisma`・seed
- BE: dto / service / use-case / controller / `app.module.ts`・同じレスポンスを組み立てる全箇所
- iOS: Domain / Network / Features / Composition Root
- docs: 01〜05・必要なら 07/09 との整合

### ④ エッジケースの機械的列挙

空/ゼロ・既存データ共存・冪等・並行・親削除 orphan・オフライン/同期失敗・タイムゾーン。

### ⑤ 出力: 検証可能な分解

- 受入基準 → テストケース（Red 先行・AC-ID）
- BE⇔iOS なら API 契約を書き切る
- 直列必須と並列可能を区別
- 要確認には仮定を添える。スコープ外を明記

## よくある間違い

| 間違い | 現実 |
|---|---|
| 要件文言から直接タスク分解 | 既存実装・未配線を見落とす |
| 最初の案をそのまま採用 | 却下案のない計画は設計ごと手戻り |
| 影響を「主要ファイル」だけ | 同じデータを組み立てる箇所は複数 |
| 死にコードを手本にする | 呼び出し元を先に確認 (IOS-1) |

## 実例メモ

名義帳で「画面が無い」ように見えても Feature や API 雛形が眠っていないか①で確認する。
失敗パターンが溜まったら本節を更新する。
