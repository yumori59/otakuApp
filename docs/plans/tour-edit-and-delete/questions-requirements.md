## Q2. 「ツアーの編集」で変えられるのは何か

BE の `UpdateTourDto`（`apps/api/src/tours/dto/update-tour.dto.ts:8-19`）は **`name` と `artist_name_raw` だけ**。
公演名・会場・公演日は `events` 側で、これは既に申込編集（`docs/plans/application-edit/`）でできる。

| 選択肢 | 内容 |
|---|---|
| **A（暫定採用）** | ツアー名 + アーティスト名の 2 項目のみ。公演の編集は従来どおり申込編集から |
| B | ツアー編集画面から配下の公演も一覧編集できるようにする（工数大） |

## Q3. ツアーを削除したとき、配下の公演・申込はどうなるか ★最重要

BE の `tours.remove`（`apps/api/src/tours/tours.service.ts:78-91`）は **連鎖しない**。
一方 iOS の `ApplicationStore.groupApplications`（`Stores/ApplicationStore.swift:314-317`）は
`tour(for:)` が nil の申込を**黙って捨てる**ため、連鎖させないと
「ツアー表からは消えるのにリストと件数には残る幽霊申込」になる。

| 選択肢 | 内容 |
|---|---|
| **A（暫定採用）** | 配下の公演・申込・同行者もまとめて削除する。確認ダイアログに「公演 N 件・申込 M 件も削除されます」を出す |
| B | ツアーだけ削除して申込は残す（残った申込はツアー表に出ない。表示の作り替えが別途必要） |
| C | 申込が 1 件でもあるツアーは削除できない（ツアー表に出るツアーは必ず申込を持つので、実質いつも押せないボタンになる） |

## Q4. 共有中のツアーを削除したらどうするか

サーバーは削除済み tour の共有を `SHARE_INVALID` にする（`shares/board/use-cases/resolve-share.use-case.ts:108-121`）。
つまり共有相手は「無効なリンクです」になる。

| 選択肢 | 内容 |
|---|---|
| **A（暫定採用）** | 確認ダイアログで「共有中の相手はこのツアー表を開けなくなります」と警告するだけ。共有リンクは自動失効させない |
| B | 削除と同時に共有リンクを失効（`DELETE /v1/shares/:id`）させる。ネットワーク必須になり、オフライン削除と原子性が取れない |

## Q5. 既にあるツアー名へリネームしたらどうするか

サーバーは `(owner_id, name)` の unique 制約で拒否する。**論理削除済みの同名ツアーとも衝突する**
（`sync.service.ts:363-379` のコメントと事前チェック）。

| 選択肢 | 内容 |
|---|---|
| **A（暫定採用）** | 保存時にローカルで事前チェックし、「同じ名前のツアーが既にあります」と出して保存させない |
| B | 同名ツアーへ**統合（マージ）**する。配下の公演を既存ツアーへ付け替える。挙動が重く、取り消せない |
| C | サーバーの reject に任せる。UI 上は成功して見えるのに同期だけ永久に失敗する（`SyncEngine.failureMessage:139-147` は「1件の変更を同期できませんでした」としか出せない）ので採らない |
