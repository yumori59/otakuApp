# 堅牢な実装 (着手前の影響半径測定と完了前セルフレビュー)

## Overview

品質は「書いたコードが正しいか」だけでは閉じない。**影響半径を着手前に測り、完了前に diff を読み直す**。
最頻の失敗は **file-local 思考**（変更ファイル内だけ見て対向レイヤーを見ない）。

## ステップ

### ① 着手前: 影響半径

1. 変更シンボルをリポジトリ横断 grep（`apps/api` 全体 / `meigicho` 全体）
2. API 契約の対向を確認（BE ↔ iOS Domain/Network）。ズレは黙って欠落しやすい (IOS-2)
3. 知識重複を列挙: Prisma ↔ NestJS dto ↔ iOS、enum 散在、UUID 前提、docs
4. 類似既存実装を 1 つ精読して平仄

### ② テスト設計

受入基準 + 空/nil/境界/冪等/未知 enum/他ユーザー id/並行/TZ。
iOS のみは手動確認手順に翻訳。

### ③ 実装中

TDD・平仄・エラーハンドリングは rules / agent 定義が正。

### ④ 完了前セルフレビュー

`git diff` を通読。①の影響箇所が「対応済み」か「残課題」か照合。

### ⑤ 報告

検証ゲート証拠 + 影響半径の扱い。BE なら iOS 追従要否、iOS なら BE 整合を 1 行。
調べていないなら「調べていない」と書く。

## よくある間違い

| 間違い | 現実 |
|---|---|
| 変更ファイル内だけ確認 | レイヤー境界を越えて grep |
| 「BE だけだから安全」 | レスポンス/enum は iOS と共有 |
| 指示された検証だけ | 影響が外に及ぶなら関連テストも |
| diff を読み直さない | 消し忘れ・巻き込み |

## 実例メモ

ID 前提を schema / docs と突き合わせずに検証を足すと本番で死ぬ経路になる (BE-1)。
観測後に本節へ実例を追加する。
