## 1. 最大のリスク: 「名義貸し・転売支援アプリ」と受け取られること

> **注記**: 本節は法的助言ではありません。法令・FC規約の解釈はリリース前に専門家へ確認してください。
> ここで述べるのは「リスクがどこにあるか」と「実務的にどう低減するか」に限られます。

### 1.1 何が問題なのか

**(a) ファンクラブ規約との関係**

多くのファンクラブ規約は、会員本人以外による申込、会員資格・会員番号の貸借や譲渡を禁止しています。本アプリは「家族・友人の名義でも申し込んだ記録を管理する」機能を持つため、**FC規約に違反する行為を前提としたアプリだ、と読まれる余地**があります。

FC規約はFCと会員の間の私法上の契約であり、アプリ運営者はその当事者ではありません。しかしプラットフォーム（Apple）は「第三者の規約に違反する行為を助長するアプリ」をガイドライン上問題視しうる立場にあります。**法的責任の有無とは別の次元で、公開可否が決まります。**

**(b) チケット不正転売禁止法との関係**

「特定興行入場券の不正転売の禁止等に関する法律」は、特定興行入場券の不正転売および不正転売目的の譲受けを禁止しています。本アプリは**チケットの売買・譲渡・価格提示を一切扱わない**ため直接の適用対象ではありませんが、①「複数名義で応募する」記録を扱うため**転売目的の大量申込を管理するツールとしても使える**構造がある、②金額フィールド（年会費 `fee`、将来の遠征費・チケット代 `price_yen`）があると「取引の記録に見える」余地が生まれる、という2点で近接します。

**(c) App Store Review Guidelines との関係**

| 該当しうる条項 | 想定される指摘 |
|---|---|
| 1.1（不快なコンテンツ） | 他者の権利や規約を侵害する行為を助長するアプリと判断される |
| 4.3（スパム / 重複） | 「当選確率を上げるツール」というカテゴリでの機能重複・低価値と見られる |
| 5.0 / 5.1.1（法的要件・データ収集） | 第三者の個人情報を必要以上に収集している、法令に反する用途 |
| 5.6（デベロッパーの行動規範） | ストア説明文と実際の用途が乖離していると判断される |

**リジェクトの実務的な怖さは「一度そう見られると覆すのが難しい」ことです。** 審査は文面ではなく
機能と訴求の総体を見ます。したがって対策は「言い方を変える」ことではなく、
**「そう見えない製品にする」ことでなければ機能しません。**

### 1.2 対策: 訴求の統一（名称・スクリーンショット・説明文）

プロダクトの訴求を **「家族や友人と一緒に応募した記録を管理し、会費の更新を忘れないためのアプリ」**
に統一します。J1（更新期限を落とさない）を第一の価値として前面に出し、
J2/J3（誰がどこに申し込んだか・当落の記録）を副次的な価値として説明します。

**この順序が重要です。** 「複数名義の管理」を第一に置くと名義管理ツールに見え、
「更新期限のリマインダー」を第一に置くと会員管理ツールに見えます。後者を選びます。

#### App Store 説明文ドラフト（日本語・約330字）

```
参戦名義帳は、ファンクラブの会員情報と、家族や友人と一緒に応募したライブの記録を、
1か所にまとめて管理するアプリです。

会員番号や更新日を登録しておくと、更新期限が近づいたときに通知でお知らせします。
うっかり期限を過ぎて会員資格を失ってしまう、という事故を防げます。

「どの公演に、誰と、いつ申し込んだか」「結果はどうだったか」「座席はどこだったか」を
記録でき、ツアー単位の一覧表で見返すことができます。
一緒に応募した家族や同行者には、読み取り専用のリンクで必要な範囲だけ共有できます。
氏名や会員番号は、共有時は既定で隠されます。

すべての情報はご自身で入力していただくものです。
チケットの売買・譲渡に関わる機能は一切ありません。記録と共有のためのアプリです。
```

**この文面の設計意図**

- 第1段落で「会員情報の管理」と言い切り、名義の複数性を主題にしない。
- 第2段落で J1 を具体的な便益として書く。ここが最も強い訴求。
- 第3段落で記録機能を説明するが、**主語を「公演」と「結果」にして「名義」を主語にしない**。
- 第4段落でプライバシー配慮を明示（審査担当者への説明も兼ねる）。
- 最終段落で**手入力であること**と**売買機能がないこと**を明示。これは説明文でありながら、
  実質的にはレビューノートの要約として機能します。

#### アプリ名・サブタイトル

| 項目 | 採用 | 避ける |
|---|---|---|
| アプリ名 | 参戦名義帳 | 「名義管理」「複数名義」「当選確率」を含む名称 |
| サブタイトル（30字） | ファンクラブの更新期限と申込の記録 | 「複数名義をまとめて管理」 |
| キーワード | ファンクラブ, 会員, 更新, 期限, リマインダー, ライブ, 記録, 当落, 座席, 遠征 | 転売, 譲渡, 定価, 名義, 複垢, 当選確率, リセール |

> アプリ名に「名義」が含まれることは受容します。日本語として「名義帳＝会員情報の帳簿」であり、
> 説明文・スクリーンショットが一貫していれば誤読リスクは限定的と判断します。ただし**審査で名称を
> 指摘された場合の代替案**を事前に用意します: 「ファンクラブ手帳」「参戦手帳」「FC更新メモ」。

#### スクリーンショット構成（5枚）

| # | 画面 | キャプション |
|---|---|---|
| 1 | ホーム（`screenHome`） | 更新期限が近い会員情報を、ひと目で |
| 2 | 名義詳細（`screenIdentityDetail`） | 会員番号・更新日・年会費をまとめて記録 |
| 3 | 申込一覧（`ticket-row`） | どの公演に誰と申し込んだかを一覧で |
| 4 | ツアー表（`screenApplicationsTable`） | ツアー単位で結果と座席を見返す |
| 5 | 共有プレビュー（`screenSharePreview`） | 一緒に応募した人へ、必要な範囲だけ共有 |

**映してはいけないもの**: ①名義が5件以上並んでいる状態（「大量の名義を管理するアプリ」に見える。**最大4件まで**）②会員番号のフルパターン（下4桁マスク状態を映す）③実在するアーティスト名・FC名・会場名（モックの `STELLARIS` / `ORBIT` / `陽炎` はこの目的で架空名になっている）④当選ばかりが並んでいる画面（「よく当たるアプリ」という誤読を招く。当選・落選・申込中を混在させる）。

### 1.3 避けるべき表現 / 推奨する表現

**社内用語とストア用語を分けます。** 設計ドキュメント内では「名義を貸してくれた人」と書いてよいが、
ユーザーに見える文言・ストア掲載文では下表の右列だけを使います。

| 避ける（禁句） | 推奨する表現 |
|---|---|
| 当選確率を上げる / 当たりやすくなる | 申込の記録を残す / 結果を見返す |
| 名義を増やす / 名義を確保する | 家族や友人の会員情報を登録する |
| 複数申込で確実に / 数を打つ | 誰がどの公演に申し込んだかを整理する |
| 名義貸し / 名義借り / 借りている名義 | 一緒に応募した家族・同行者 |
| 複垢 / 複数アカウント / サブ垢 | （使用しない） |
| 転売 / 定価 / 譲渡 / リセール / 買い取り | （使用しない。1文字も使わない） |
| 当落予測 / 当選傾向の分析 | 過去の当落の記録 |
| 神席 / 良席 | 座席の記録 |
| 名義を管理する（アプリの主機能として） | ファンクラブの会員情報を管理する |
| 遠征仲間を探す / 名義を募る | （使用しない） |

**適用範囲**: App Store 説明文・サブタイトル・キーワード・スクリーンショットのキャプション・
アプリ内コピー・通知本文・プライバシーポリシー・利用規約・LP・SNS・リリースノート・サポートFAQ。
`07-monetization.md` のペイウォールコピーも同じ規約に従います（「4件目の名義を登録するには」は
「名義を増やす」ではなく登録行為の説明なので許容範囲、と判断）。

**運用**: 上表を CI のテキスト検査に組み込みます。ローカライズ用の文言ファイル（`Localizable.strings`）
と App Store メタデータを対象に、禁句リストへの一致で CI を失敗させます。

### 1.4 実装してはいけない機能（明示リスト）

以下は**要望があっても実装しません。** 収益機会や利便性より、公開可否を優先します。

| # | 禁止する機能 | 理由 |
|---|---|---|
| 1 | チケットの譲渡・受け渡し機能（相手の指定、受け渡し完了の記録を含む） | 譲渡の仲介と見なされる |
| 2 | 価格入力を伴う「取引」（相手への請求、立替の精算、送金、割り勘の決済） | 取引プラットフォーム化。1.5 の線引き参照 |
| 3 | チケットの売買掲示板・出品・希望価格の掲示 | 不正転売の場そのもの |
| 4 | 他ユーザーとの名義マッチング（名義を貸したい人／借りたい人のマッチング） | 名義貸しの仲介そのもの |
| 5 | FCサイトへの自動ログイン・スクレイピング・代行申込・自動フォーム入力 | 各サイト規約違反、不正アクセス関連法規のリスク、`00` の Non-goal |
| 6 | 当選確率の予測エンジン・当選傾向スコア・「この名義が当たりやすい」表示 | アプリの目的を「当選確率を上げること」に変えてしまう |
| 7 | 公開タイムライン・当選報告のフィード・ランキング | 当選自慢の場になり、譲渡の呼びかけが必ず現れる |
| 8 | ユーザー間のダイレクトメッセージ | 譲渡・売買の交渉に使われる。監視できない |
| 9 | 会員番号の一括インポート・CSV取り込み | 名義の大量管理を明確に支援する機能に見える |
| 10 | 名義数の無制限性を訴求する機能（「あなたの名義数ランキング」等） | 論外 |

**この禁止リストは `00-design-basis.md` の Non-goals と `07-monetization.md` の
「将来の収益源候補」の否決理由と一致させています。3つのドキュメントで齟齬が出ないこと自体が防御です。**

### 1.5 金額フィールドの設計上の線引き

モックには `membership.fee`（年会費）があり、将来 `price_yen`（チケット代）のような
自分の支出を記録するフィールドを持つ可能性があります（`07` の「遠征費管理」）。
これらは**「自分の支出記録」に厳格に限定**し、他者への請求・送金・出品に一切つながらないことを
**設計で担保**します。

| 担保する方法 | 具体 |
|---|---|
| **データモデルで担保** | 金額カラムを持つ行は必ず `owner_user_id` に紐づく。**「支払う相手」「請求先」を表すカラムを一切作らない**。`payer_identity_id` のような他者を指すカラムを作らない |
| **共有で担保** | 共有リンクのペイロード（`buildTourPayload` 相当）に**金額を一切含めない**。共有先に金額が見えることがない。`03-database.md` の共有ビューから金額カラムを物理的に除外する |
| **エクスポートで担保** | CSVエクスポートは金額を含むが、**出力先はユーザー自身のファイルのみ**。共有リンクからのエクスポートは提供しない |
| **UIで担保** | 金額の入力欄は「自分が支払った額」というラベルにする。「立替」「割り勘」「請求」という語をUIに一切出さない |
| **決済連携で担保** | 送金・決済APIとの連携を実装しない。`00` の Non-goal（決済代行・割り勘の実送金）と一致 |

**言い換えると、金額は「家計簿」の意味しか持たず、「取引」の意味を持たせない。**
この区別は審査で説明できる形にしておく必要があるため、レビューノートにも明記します。

### 1.6 審査で聞かれた場合の回答方針（レビューノート文面ドラフト）

App Store Connect の「App Review Information > Notes」に、初回申請時から以下を記載します。
**聞かれてから答えるのではなく、先に書いておく**ことでリジェクトの確率を下げます。

```
【アプリの目的】
本アプリは、ユーザーが加入しているファンクラブの会員情報（会員番号・更新期限・年会費）と、
コンサートへの応募記録（公演名・応募日・結果・座席）を、ユーザー自身が手入力して管理する
パーソナルな記録・リマインダーアプリです。主な価値は「会員資格の更新期限を忘れないこと」です。

【本アプリに存在しない機能】
・チケットの売買、譲渡、価格の提示、出品、取引に関する機能は一切ありません。
・他のユーザーとのマッチング、メッセージ、公開タイムラインはありません。
・外部のファンクラブサイトへのログイン、スクレイピング、代行申込は行いません。
　すべてのデータはユーザーによる手入力です。ネットワーク通信はユーザー自身のデータの
　バックアップ・同期（当社が運営するAPIサーバー / Google Cloud）と、
　広告配信（Google AdMob）のみです。

【「家族」「友人」として登録される情報について】
ユーザーは、一緒にコンサートへ応募した家族や同行者を識別するための呼び名（ニックネームでも可）と、
任意項目としてのファンクラブ会員番号を登録できます。これはユーザーが本人の同意を得て
入力することを前提としており、初回登録時に同意確認のダイアログを表示しています
（スクリーンショット: consent_dialog.png を添付）。
会員番号は端末上およびサーバー上で暗号化して保存し、画面表示は既定で下4桁のみです。
入力を省略することもできます。

【共有機能について】
共有はランダムなトークンを含むURLによる読み取り専用のWebビューです。
氏名は既定でマスクされ、会員番号と金額は共有内容に一切含まれません。
リンクはユーザーがいつでも無効化でき、既定の有効期限は90日です。

【サブスクリプションについて】
「参戦名義帳 Plus」（月額 / 年額）は、管理できるプロフィール（名義）の件数上限（無料版は3件）を
解除し、広告を非表示にし、端末間同期・統計・エクスポートを利用可能にするものです。
価格・期間・自動更新の説明、利用規約とプライバシーポリシーへのリンク、
「購入を復元」ボタンをすべて購入画面に表示しています。

【確認手順】
テスト用アカウント: review@example.com / (パスワードは別途 App Store Connect に記載)
Plus の確認: 設定タブ →「参戦名義帳 Plus」→ Sandbox 購入
名義上限の確認: 名義タブ → ＋ を4回タップすると4回目に購入画面が表示されます
アカウント削除の確認: 設定タブ → アカウント → アカウントを削除
```

**追加で聞かれた場合の回答方針**

| 想定質問 | 回答方針 |
|---|---|
| 名義貸しを助長するアプリではないか | 記録機能のみを提供し、名義の貸借を仲介・斡旋・推奨する機能を持たない。同行者の登録は「誰と一緒に行くか」の記録であり、家族での応募が主要な想定利用。訴求も一貫して「更新期限のリマインダー」である |
| なぜ他人の個人情報を収集するのか（5.1.1） | 収集ではなくユーザー自身の記録。氏名はニックネーム可、会員番号は任意で省略可。**両方とも未入力でも主要機能（更新期限の通知）は動作する**＝必要最小限である |
| チケットの転売に使われないか | 価格・譲渡・取引・ユーザー間通信の機能が存在せず、アプリ内で転売行為を完結できない。将来も実装しない方針を 1.4 で明文化 |
| アプリ名の「名義」は何を指すのか | 「会員名義」＝ファンクラブの会員資格の名前を指す一般語で、アプリ内では「プロフィール」として実装されている。指摘が続く場合は 1.2 の代替名に変更する |

## 2. 個人情報保護

> **注記**: 本節は法的助言ではありません。個人情報保護法の適用関係は事実関係により変わります。
> 特に「委託」「越境移転」「漏えい報告義務」の判断は、リリース前に弁護士・専門家へ確認してください。

### 2.1 法的な立ち位置の整理

このアプリは**ユーザー本人以外（家族・友人）の氏名とファンクラブ会員番号**を扱います。
氏名と会員番号の組み合わせは特定の個人を識別しうるため、個人情報として扱う前提で設計します。

| 主体 | 立ち位置 | 帰結 |
|---|---|---|
| **ユーザー（個人）** | 家族・友人の情報を私的に記録している。個人情報保護法上、個人が私的な目的で個人情報を扱う場合は個人情報取扱事業者の義務の**適用除外となる余地**がある | ユーザー側に法的義務が生じにくい。ただしFC規約上の責任は別（1.1） |
| **アプリ運営者（Phase 0）** | ローカル完結でサーバーに送信しない。運営者は**個人データを取り扱っていない** | 安全管理措置の対象となるデータを保有しない。これが Phase 0 をローカル完結にする副次的な利点 |
| **アプリ運営者（Phase 1 以降）** | クラウド同期を開始した時点で、**ユーザーから第三者の個人情報の預託を受ける立場**になる | **安全管理措置義務が生じる。** 以下すべてが該当しうる |

**Phase 1 以降で運営者に生じる主な義務（要確認事項として整理）**

| 論点 | 整理 |
|---|---|
| 安全管理措置 | 組織的・人的・物理的・技術的措置を講じる必要がある。2.3 / 2.4 / 4章がその実装 |
| 委託先の監督 | Google Cloud（Cloud Run / Secret Manager / Cloud KMS / Cloud Logging、将来オプションで Cloud SQL）、**Supabase Inc.（PostgreSQL ホスティング）**、Neon（代替で運用する場合）、Google（AdMob）、RevenueCat、Sentry 等は「委託先」に相当しうる。**選定基準と監督方法を文書化**する（本書がその文書）。※共有専用 Web（Cloudflare / Vercel）は採用しない（2026-08-05） |
| 越境移転 | Cloud Run は東京（`asia-northeast1`）、Supabase Postgres は東京（`ap-northeast-1`）に固定する（Neon / Cloud SQL 利用時も東京）。Firebase Authentication は使わない方針だが、万一置く場合は保存リージョンを選択できないため情報を限定する。記録本体は自前のPostgreSQLに置く。外国にある第三者への提供・委託の規律への抵触リスクを構造的に下げるため。`06-infrastructure.md` と整合させる |
| 利用目的の特定・通知 | プライバシーポリシーで明示（2.6） |
| 漏えい時の対応 | 一定の要件（要配慮個人情報、財産的被害のおそれ、不正目的、**1,000人超**等）で個人情報保護委員会への報告と本人通知の義務が生じうる。**手順を事前に用意する**（4.5） |
| 開示・訂正・削除の請求 | 保有個人データについて請求に応じる体制が必要（2.5） |

**実務的な結論**: 「ユーザーが個人的に使う分には問題が小さいが、**運営者は預かった瞬間から責任を負う**」。したがって設計方針は **「そもそも預からない選択肢を用意する」＋「預かるものは運営者にも読めない形にする」** になります。

### 2.3 暗号化方針

#### 端末内（iOS）

| 対象 | 方式 |
|---|---|
| SwiftData ストア全体 | iOS の Data Protection。ファイル保護クラスは `NSFileProtectionCompleteUnlessOpen`（バックグラウンドでの通知スケジュール更新があるため `Complete` は使えない） |
| 会員番号（`memberships.member_no`） | **アプリ層で AES-GCM 暗号化**（CryptoKit）。SwiftData には暗号文（`Data`）として保存 |
| 暗号鍵 | Keychain に保存。`kSecAttrAccessible` = `AfterFirstUnlockThisDeviceOnly` … **ただし機種変更問題があるため 2.4 で再検討** |
| バックアップ | 会員番号は暗号文のまま iCloud バックアップに含まれる（鍵がなければ復号不可） |

#### サーバー（Supabase）

| 層 | 方式 |
|---|---|
| ストレージ暗号化 | Supabase / AWS の保存時暗号化（運営者が有効化を確認するだけ。これ単体では「運営者は読める」） |
| 転送時 | TLS 1.2 以上 |
| **機微カラム（会員番号）** | **アプリ層で暗号化してから送信する（＝運営者も復号できない）** |
| その他のカラム（氏名、公演名、当落、座席、メモ） | 平文で保存（運営者は技術的に読める）。ただしRLSでユーザー本人以外はアクセス不可 |

#### 「運営者も復号できない設計」の是非とトレードオフ

会員番号のみを E2EE（クライアントサイド暗号化）とし、他のカラムは平文にします。
この非対称な選択にははっきりした理由があります。

| | 会員番号を E2EE にする | 全カラムを E2EE にする | E2EE にしない |
|---|---|---|---|
| 漏えい時の被害 | **会員番号は漏れない** | 何も漏れない | 全部漏れる |
| 説明責任 | 「最も機微な項目は運営者も見られません」と言える | 同左（より強い） | 説明が弱い |
| サーバー側検索・集計 | 会員番号での検索は不可（**許容できる。会員番号で検索するユースケースがない**） | **不可。`v_identity_stats` / `v_upcoming_renewals` / `v_tour_matrix` がすべて作れなくなる** | 全て可 |
| 共有リンク（Webビュー） | 影響なし（会員番号は共有に含めない） | **成立しない**（Webから復号鍵にアクセスできない） | 影響なし |
| サポート対応 | 「会員番号が消えた」に対応できない（免責を明記する） | ほぼ全ての問い合わせに対応できない | 対応できる |
| 実装コスト | 中 | 高 | 低 |

**決定: 会員番号のみ E2EE。** 全カラム E2EE は `00-design-basis.md` の中核機能
（集計ビュー、Webの共有リンク）と両立しません。一方、会員番号は
「検索も集計も共有もしない、ただ保存して下4桁を見せるだけ」の項目なので、E2EE の代償がほぼゼロです。
**リスクが最大でコストが最小の1項目だけを E2EE にする**のが、この設計の合理点です。

### 2.4 鍵管理: 機種変更で復号不能になる問題

`ThisDeviceOnly` の Keychain 項目は端末間で移行されないため、機種変更すると会員番号が復号できません。
これは「実装後に気づくと手遅れ」な種類の問題なので、先に方式を決めます。

| 方式 | 内容 | 利点 / 欠点 |
|---|---|---|
| **(a) iCloud Keychain 同期**（採用） | `kSecAttrSynchronizable = true` + `AfterFirstUnlock`。iCloud Keychain 経由で新端末へ引き継がれる | ユーザー操作ゼロで移行でき実装が最も単純 / iCloud Keychain を無効にしているユーザーは鍵を失う |
| (b) パスフレーズ由来鍵 | パスフレーズから HKDF / Argon2id で鍵導出 | iCloud に依存せず最も強い / 忘れると永久に復号不可。UXの摩擦がこの規模には過剰 |
| (c) 復旧キーの書き出し | 32バイト鍵を Base32 文字列としてユーザーに保存させる | (b) より軽い / 保存してもらえない |
| (d) サーバー側で鍵を管理 | Supabase Vault に鍵を置く | 移行が確実 / **運営者が復号可能になり 2.3 の目的が失われる** |

**決定: (a) を既定とし、(c) を任意のバックアップ手段として設定画面に置く。(d) は採用しない。**

**鍵を失った場合の挙動（必ず実装する）**

```
会員番号を表示できません

この端末では、以前に登録された会員番号を復号するための鍵が見つかりませんでした。
（機種変更時に iCloud キーチェーンが無効だった場合などに起こります）
会員番号を再度入力していただくと、以降は正しく表示されます。
更新期限や年会費、申込の記録には影響していません。

[ 会員番号を再入力する ]   [ この会員番号を空にする ]
```

**設計上の要点**: 鍵の喪失が**その1フィールドだけの喪失に閉じる**こと。
氏名・更新日・年会費・申込履歴は平文なので、アプリ全体が壊れることはありません。
「暗号化で全データが読めなくなった」という最悪の事故を構造的に防いでいます。

### 2.7 App Privacy（プライバシーラベル）の申告内容

App Store Connect の App Privacy で申告する内容を、実装前に確定させます。
**申告と実装が食い違うと 5.1.1 / 5.6 でのリジェクト・削除の原因になります。**

| データ種別 | 収集 | 用途 | ユーザーIDに紐づくか | **トラッキング** | 由来 |
|---|---|---|---|---|---|
| 連絡先情報 > メールアドレス | あり | アプリの機能（アカウント） | 紐づく | **なし** | Sign in with Apple（プライベートリレー可） |
| 識別子 > ユーザーID | あり | アプリの機能 | 紐づく | **なし** | Supabase Auth / RevenueCat `app_user_id` |
| **識別子 > デバイスID** | あり | **サードパーティ広告** | **紐づかない** | **なし（2.8 の方針による）** | Google AdMob（IDFV / 広告ID） |
| ユーザーコンテンツ > その他のユーザーコンテンツ | あり | アプリの機能 | 紐づく | **なし** | 名義・会員情報・申込の記録（第三者の氏名を含みうる） |
| 購入 > 購入履歴 | あり | アプリの機能 | 紐づく | **なし** | StoreKit / RevenueCat |
| 使用状況データ > 製品の操作 | あり | 分析、アプリの機能 | 紐づく | **なし** | 自前の `analytics_events` |
| 診断 > クラッシュデータ / パフォーマンス | あり | アプリの機能 | 紐づかない | **なし** | Sentry |
| 位置情報 / 健康 / 財務情報 / 連絡先 / 検索履歴 / 写真 | **なし** | — | — | — | 収集しない |

**「収集しない」を維持する項目を明示しておくことが重要です。** 将来の機能追加でこれらに触れる場合は
プライバシーラベルの更新が必要になるため、本表を仕様変更時のチェックリストとして使います。

### 2.8 AdMob と ATT（AppTrackingTransparency）の扱い

> **注記**: 本項の判断は法令解釈ではなく、プラットフォーム要件と事業判断の整理です。

**決定: Phase 1 は非パーソナライズ広告（NPA）固定でリリースし、ATT プロンプトを表示しない。**

| 選択肢 | 内容 | 結果 |
|---|---|---|
| **(a) NPA 固定・ATT なし**（採用） | AdMob のリクエストに `npa=1` を常に設定。ATT プロンプトを出さない。App Privacy の「トラッキング」を**なし**で申告 | eCPM が 30〜50% 低下（`07` 7.7 でこの低下を織り込み済み）。プライバシーラベルが単純で、審査での説明も容易。ユーザーの信頼を得やすい |
| (b) ATT プロンプト表示 → 許諾時のみパーソナライズ | 許諾率25〜35%を想定 | eCPM が 10〜20% 改善。ただしプロンプトの文面・タイミングが審査対象になり、「トラッキングあり」の申告が必要 |

**(a) を選ぶ理由**

1. **このアプリは他人の個人情報を預かる。** その同じアプリが「あなたを追跡させてください」と聞くのは、信頼の構造として整合しません。プライバシーを訴求点にする方がこのプロダクトでは価値が高い。
2. `07` 8.8 の感度分析で **eCPM 保守ケース（¥150）でも黒字**と確認済みで、NPA による低下を吸収できる。
3. App Privacy の「トラッキング」を「なし」で申告できると、審査・説明・ポリシー文面のすべてが単純になる。
4. **Phase 2 で A/B できる。** NPA → ATT 導入は後からできるが、逆（一度出したプロンプトをやめる）は印象上やりにくい。**制約の弱い方から始める**のが順序として正しい。

**実装上の注意**: `GADMobileAds` の初期化時に `npa=1` を `GADExtras` で設定し、AdMob 管理画面でも非パーソナライズ配信を有効化。**`NSUserTrackingUsageDescription` を Info.plist に入れない**（入れておくと審査で「なぜプロンプトを出さないのか」と聞かれる余地が生まれる）。`SKAdNetworkItems` は AdMob の指示に従って設定（アトリビューション用でトラッキング申告には影響しない）。

### 4.2 各脅威への対策

#### T1: 共有トークン

| 項目 | 仕様 |
|---|---|
| 生成 | **32バイトの暗号論的乱数**（`SystemRandomNumberGenerator` / `crypto.getRandomValues`）→ Base64URL（43文字） |
| エントロピー | 256ビット。総当たりは現実的に不可能 |
| DB保存 | **平文を保存しない。** `share_links.token_hash = sha256(token)` のみを保存。URLの平文トークンは発行時に一度だけユーザーに渡す |
| URL形式 | `https://meigicho.app/s/<token>`。**パスに置きトークンをクエリに入れない**（Referer やログへの漏出を減らす） |
| 有効期限 | 既定 **90日**。Plus は任意設定可（最大1年）。`expires_at` |
| 失効 | ユーザーがいつでも無効化可（`revoked_at`）。アカウント削除時に全件即時失効 |
| 異常検知 | `view_count` / `last_viewed_at` / `distinct_ip_count`（ハッシュ化したIPの概数）。**24時間で30回以上の閲覧**があった場合、ユーザーに通知して失効を促す |
| レート制限 | Edge Function で IP あたり **10 req/min**。超過は 429 |
| **存在の隠蔽** | **無効・期限切れ・存在しないトークンすべてに同じ 404 を返す**（410 や「期限切れです」と返すと、トークンの存在が推測できてしまう）。ただしユーザー体験のため、**自分が発行したリンク**についてはアプリ内で状態を確認できる |
| インデックス化防止 | `X-Robots-Tag: noindex, nofollow` / `<meta name="robots">` / `Referrer-Policy: no-referrer` |
| コンテンツ | 会員番号・金額を含めない（1.5 / 2.2 #5）。氏名は既定でマスク |

#### T2: RLS の設定漏れ（最重要）

RLS は「書き忘れると全公開になる」性質があるため、**テストの自動化が唯一の実効的な対策**です。

```
テスト対象: 全テーブル × 全操作（SELECT/INSERT/UPDATE/DELETE） × 3ロール
  ロール1: anon（未認証）           → 期待: 全テーブルで全操作が拒否
  ロール2: authenticated ユーザーA  → 期待: 自分の行のみ全操作可
  ロール3: authenticated ユーザーB  → 期待: ユーザーAの行に一切アクセスできない
```

| 項目 | 仕様 |
|---|---|
| フレームワーク / タイミング | pgTAP（`supabase test db`）または Deno test + PostgREST 経由の実アクセス。**CI で必ず実行**（`supabase db reset` → マイグレーション適用 → テスト）。失敗したらマージ不可 |
| 網羅性の担保 | `pg_catalog` から**テーブル一覧を動的に取得**し、テストが書かれていないテーブルがあれば**テスト自体を失敗させる**。加えて `SELECT relname FROM pg_class WHERE relrowsecurity = false` が `public` スキーマで空であることを検証（RLS 有効化の漏れ検出） |
| ビュー | `v_*` は `security_invoker = true` を設定し、基底テーブルの RLS が効くことをテストで確認 |

```
   前項と同様に本人の同意を得なければなりません。
3. 前二項に違反して生じた紛争および損害について、利用者が自らの責任と費用で
   解決するものとし、当社は責任を負いません。
4. 当社は、第三者本人から申し出があった場合、当該第三者の情報の削除その他
   必要な措置を講じることがあります。
```

#### (3) 記録の正確性・通知の到達を保証しない

```
第○条（記録および通知に関する免責）
1. 本サービスに登録される情報は、すべて利用者自身が入力するものであり、
   当社はその内容の正確性、完全性、最新性について保証しません。
2. 本サービスが提供する更新期限、当落発表日等の通知は、利用者の利便のための
   補助的な機能であり、確実な到達を保証するものではありません。
   端末の設定、通信状況、OSの仕様変更等により通知が届かない場合があります。
3. 前二項に起因して生じた損害（ファンクラブの会員資格の失効、申込期限の
   経過を含みます）について、当社は責任を負いません。
4. 利用者は、重要な期限については本サービス以外の手段でも確認するものとします。
```

### 5.2 免責文だけではリスクは消えない

**この点を明記しておくことが、本節で最も重要な内容です。** 免責文が効くのは「ユーザーとの間の民事上の責任分担」（それも一定の範囲で）だけです。効かない相手が4つあります。

| 効かない相手 | 理由 |
|---|---|
| **App Store の審査** | 審査は規約の文面ではなく、**機能と訴求の実体**を見る |
| **ファンクラブ運営者からの申し立て** | 規約に「ユーザーの責任」と書いてあっても、アプリが規約違反を助長していると評価されれば申し立ての対象になりうる |
| **報道・SNSでの評判** | 「利用規約に書いてある」は世論に対して機能しない |
| **個人情報保護法上の運営者の義務** | ユーザーに責任を転嫁する条項で、運営者の安全管理措置義務が消えることはない |

**したがって対策の優先順位は次の通りです。**

```
1. 機能を持たない（1.4 の禁止リスト）      ← 最も強い。実装しなければリスクは存在しない
2. データを持たない（2.2 #1 #2 の任意化）  ← 次に強い。預からなければ漏れない
3. 訴求を一貫させる（1.2 / 1.3）           ← 審査と評判に効く
4. 技術的に守る（2.3 / 4章）               ← 持たざるを得ないものを守る
5. 免責文を書く（本節）                    ← 最後の防御。これ単体では機能しない
```

免責条項は「1〜4をやった上で、それでも残る責任の分担を定めるもの」です。**免責文を書いたから機能を実装してよい、という順序の逆転が最も危険**です。

### 6.1 対策の実施順序

```
【Phase 0 と同時に着手（後回しにできない）】
  R1 訴求の統一と禁句リスト   … 名前・説明文・UIコピーが後から全部書き換わるのを防ぐ
  R1 禁止機能リスト（1.4）    … 機能を作ってから消すのは最もコストが高い
  R4 会員番号の任意化と暗号化 … データモデルに関わるため後付け不可
  R19 通知の多重化            … Phase 0 の主機能
【Phase 1 の着手時（サーバー導入と同時）】
  R3 RLS 自動テスト（サーバー導入の前提条件）／R6 共有トークン／R5 鍵管理とシークレット検査
【Phase 1 の申請前（申請をブロックする項目）】
  R7 Privacy Manifest / App Privacy ／ R8 アカウント削除 ／ R9 サブスクの表示要件
  R18 規約・ポリシーの専門家レビュー
```

**R1 と R4 を Phase 0 に置いているのが本書で最も重要な主張です。** この2つは「後から直せる問題」ではなく、名称・訴求・データモデルという**やり直しが最も高くつく層**に埋め込まれています。`00-design-basis.md` の「7. 最大のリスク」が設計前提サマリに置かれている理由もここにあります。
